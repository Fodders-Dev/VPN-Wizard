# A/B: VLESS+Reality поверх XHTTP (+mux) — тест против TCP-Vision

Готовый профиль: [`config-profile-vless-reality-xhttp.json`](config-profile-vless-reality-xhttp.json).
Структура заземлена на официальный `XTLS/Xray-examples/VLESS-XHTTP-Reality/server.jsonc`.

**Зачем.** С 2026 ТСПУ ловит «пачку параллельных TLS к одному хосту» — это бьёт по
твоему дефолту (Reality+TCP+Vision без mux). XHTTP схлопывает соединения в одно
долгоживущее и размазывает трафик по HTTP-транзакциям (плюс XMUX на клиенте) — должно
проходить поведенческий анализ лучше. Но у XHTTP+Reality были баги парсинга в части
клиентов (Xray issue #6048, апрель 2026) — поэтому **это A/B, а не замена.**

> ⛔ **НЕ удаляй свой TCP-Vision-хост.** Он остаётся страховкой: если XHTTP у кого-то
> не заведётся, клиент возьмёт рабочий TCP-хост из той же подписки.

## Чем отличается от TCP-Vision (важные детали)
| | TCP-Vision (текущий) | XHTTP (этот) |
|---|---|---|
| `streamSettings.network` | `raw` | `xhttp` |
| flow у клиента | `xtls-rprx-vision` | **пусто** (Vision с XHTTP НЕ используется) |
| транспорт-настройки | — | `xhttpSettings.path` (+ `mode`) |
| порт | 443 | 8443 по умолчанию (чтобы ужиться с 443 на той же ноде) |

## Шаги
1. **Ключ Reality.** Можешь **переиспользовать** тот же `privateKey` + `serverNames`,
   что и в TCP-хосте (одинаковый SNI — норм), либо сгенерировать свежие (`docker run
   --rm ghcr.io/xtls/xray-core:latest x25519`). shortId — свой (`openssl rand -hex 8`).
2. **Path — обязательно свой, случайный.** Замени `/REPLACE_WITH_RANDOM_PATH` на
   что-то вроде `/$(openssl rand -hex 6)`. Одинаковый на сервере и в клиенте (Remnawave
   проставит сам).
3. **Порт.** По умолчанию `8443`, чтобы жить рядом с 443-TCP-Vision на одной ноде
   (открой: `sudo ufw allow 8443/tcp`). «Чистый» вариант — 443 на **отдельной ноде/IP**
   (тогда поставь `"port": 443`). Бонус: не-443 порт заодно проверяет гипотезу обхода
   «TLS-policing» проводных ISP, который срабатывает только на 443.
4. **Куда вставлять.** Два варианта, оба дают A/B в ОДНОЙ подписке:
   - добавить этот inbound **вторым** в `inbounds[]` твоего текущего Config Profile; **или**
   - создать отдельный Config Profile и назначить его инбаунд **в тот же squad**.
   Итог: у клиента в подписке ДВА хоста (TCP-Vision + XHTTP) — селектор `urltest`
   «⚡ Fastest» сам выберет живой/быстрый.

## Клиентская сторона — проверь в сгенерированной ссылке (это ловит баги)
- **Fingerprint (`fp`) = `firefox` или `edge`, НЕ chrome/safari** (Chrome-профиль uTLS
  считается «подозрительным»). Если Remnawave ставит chrome по умолчанию — поменяй в
  настройках подписки/профиля.
- В ссылке должно быть `type=xhttp` (или `mode=...`), правильный `path`, `security=reality`,
  `flow` **пустой**.
- **Пин версий клиентов.** Тестируй на СВЕЖИХ Happ / v2rayTun / Hiddify — именно на
  старых версиях всплывал `failed to read client hello`. Если на каком-то клиенте
  XHTTP не коннектится — это ожидаемо, он откатится на TCP-хост.

## Как мерить (иначе A/B бессмысленный)
На **реальных SIM всех трёх** (МТС/Мегафон/Билайн) + 1–2 проводных, **1–2 суток**:
- успешность коннекта (XHTTP-хост vs TCP-хост) по операторам;
- стабильность (не «замерзает» ли через ~15–20 КБ, как TCP-Vision на части проводных);
- скорость/пинг (speedtest внутри туннеля).
Веди простую табличку оператор × хост × (коннект / стабильность / скорость).

## Что дальше
- Если XHTTP выигрывает у части операторов — оставляешь оба хоста в подписке (это и есть
  устойчивость), у TCP роль страховки.
- Следующий протокол для подписки — **Hysteria2** (у Remnawave есть офиц. шаблон
  `example-hysteria-bbr.json`); скажи — подготовлю так же с A/B-обвязкой.
